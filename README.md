# Resu — фронтенд

Интерфейс протокола: стейкинг с выбором места в очереди на убыток.

## Запуск

```
npm install
npm run dev        # http://localhost:5173
```

Сеть выбирается через `VITE_NETWORK` в `.env` (`testnet` по умолчанию) — так
боевые адреса не покажутся случайно при локальной разработке.

Пока в `src/deployments/<network>.json` нет адресов, интерфейс показывает
инструкцию по деплою и **не притворяется работающим** на выдуманных данных.

## Проверки

```
npm run verify-deploy  # сверить развёрнутое с задуманным
npm run check      # всё сразу
npm run typecheck  # tsc
npm run selftest   # чистая логика, в Node
npm run smoke      # запуск приложения в браузероподобной среде
npm run build
```

`selftest.ts` проверяет, что сообщение, которое собирает интерфейс, побитово
совпадает с тем, что принимают контракты. Ошибка в одном бите Either-флага
или в порядке полей означает потерянный депозит, и молча — транзакция пройдёт
успешно, а долей не будет.

`smoke.mjs` собирает приложение в один IIFE и запускает его в jsdom, где
**намеренно нет нодовских глобалей**. Это отдельная проверка, потому что
selftest гоняется в Node, где `Buffer` есть, — и однажды пропустил падение
приложения в браузере на первом же импорте `@ton/core`.

Тест проверяем на негативном контроле: если убрать `import './polyfills'`
из `main.tsx`, он падает с тем самым `Buffer is not defined`.

## Публикация на GitHub Pages

Сборка и публикация настроены в `.github/workflows/pages.yml` — при пуше
в `main` прогоняются те же проверки, что и локально, и только потом деплой.

Разово в настройках репозитория: **Settings → Pages → Source: GitHub Actions**.

Две вещи, которые ломаются на Pages, если о них не знать:

**Путь.** Pages раздаёт сайт по адресу `/<репозиторий>/`, а не из корня
домена. Без `base` все ссылки на скрипты ведут в корень, и страница
открывается пустой. Значение подставляет workflow из имени репозитория,
в коде оно не зашито.

**Манифест TonConnect.** Ссылка на него строится от `BASE_URL`, а не от
корня сайта — иначе кошелёк получит 404 и ответит «invalid manifest».
После публикации приведите `url` в `public/tonconnect-manifest.json`
к реальному адресу вида `https://<аккаунт>.github.io/<репозиторий>/`,
иначе кошельки будут ругаться на несовпадение.

**Про ключ toncenter.** `VITE_TONCENTER_API_KEY` берётся из секрета
репозитория, но в статической сборке любая `VITE_*` переменная **попадает
в публичный бандл** и видна каждому. Это ключ от лимита запросов, а не от
денег, но исчерпать его может кто угодно. Для публичного сайта правильнее
свой прокси или узел, а секрет в репозитории — временное решение.

## Подключение кошелька: манифест обязан быть публичным

Кошелёк **скачивает** манифест сам, со своего устройства. Поэтому
`http://localhost:5173/tonconnect-manifest.json` не годится: кошелёк его не
видит и отвечает «invalid manifest» — даже если файл прекрасно открывается
в браузере разработчика.

Для локальной разработки положите `public/tonconnect-manifest.json` на любой
публичный https и укажите ссылку в `.env`:

```
VITE_TONCONNECT_MANIFEST_URL=https://raw.githubusercontent.com/<...>/manifest.json
```

Так сделано в syde: манифест лежит отдельным файлом в публичном репозитории.
Подойдёт и туннель (`cloudflared tunnel --url http://localhost:5173`), и gist.

В продакшене переменную можно не задавать — там origin уже публичный, и
сработает путь по умолчанию.

## RPC и лимиты запросов

Используется **фиксированный toncenter**, а не балансировщик `ton-access`.
Причина не теоретическая: ton-access раскидывает запросы по узлам, среди
которых попадаются отставшие, и на них свежеразвёрнутого контракта просто
нет — интерфейс показывал `exit_code: -13` на полностью живом протоколе.

Запросы идут **по очереди**, а не залпом. Замеры на toncenter без ключа:

| Режим | Результат |
|---|---|
| залпом (5 чтений разом) | 3 отказа `429` |
| очередь по 350 мс | 2 отказа |
| очередь по 1100 мс | без отказов, 5.2 с |

Ключ toncenter (`VITE_TONCENTER_API_KEY`, бесплатно у `@tonapibot`) снимает
лимит, и пауза падает до 120 мс. **Без ключа интерфейс заметно медленный:**
полный проход с подключённым кошельком занимает около 28 секунд против
примерно 2 с ключом.

Что сделано, чтобы это было терпимо:

- **Повтор на 429** с растущей паузой. Без него одно отклонение роняло всё
  обновление, и на экране оставались прежние числа — в том числе нулевой
  баланс, снятый до подключения кошелька. Отличить это от «у вас правда ноль»
  было невозможно.
- **Кеш выведенных адресов.** Адрес позиции и адрес кошелька жетона
  вычисляются из адресов и не меняются никогда — перечитывать их каждый раз
  значило четыре лишних запроса. После первой загрузки 9 запросов вместо 13.
- **Двухэтапная загрузка.** Пул показывается сразу (около 6 секунд), данные
  кошелька подгружаются следом. Пока баланс не прочитан, интерфейс показывает
  `…`, а не ноль.
- **Пауза отсчитывается от окончания** прошлого обновления, а не по
  расписанию: иначе обновления накладывались бы друг на друга.

Ёмкость (`lossHeadroom`) считается **на клиенте** из уже прочитанных данных,
а не отдельным запросом. Это не только экономит вызов: отдельное чтение могло
прийтись на момент между двумя изменениями, и ёмкость на экране не сходилась
бы с показанными траншами.

## Нодовские глобали

`@ton/core` и `@ton/ton` обращаются к глобальному `Buffer` напрямую. Полифилл
живёт в `src/polyfills.ts` и импортируется **первым** в `main.tsx`.

Именно модулем в исходниках, а не плагином сборки: плагин подставляет полифилл
только при `vite build`, а в dev-режиме граф остаётся без него — сборка
проходит, а `npm run dev` падает. Модуль попадает в граф одинаково в обоих
режимах, поэтому и дымовой тест накрывает оба.

## Как это связано с контрактами

| Что делает интерфейс | Куда шлёт | Что читает |
|---|---|---|
| Депозит | свой jetton wallet → vault | `trancheState`, `vaultState` |
| Заявка на выход | контракт позиции | `positionData` |
| Забрать | контракт позиции | `positionAddress` |
| Показ ёмкости | — | `lossHeadroomNow` |

**`forwardTonAmount` обязателен.** Без него кошелёк жетона не пришлёт vault'у
уведомление, жетоны лягут на его баланс, а долей не будет. Это свойство TEP-74,
не наша ошибка, — поэтому ноль здесь недопустим ни при каких условиях.

## Что показывается и почему

Ставка транша выражена **относительно базовой доходности**, а не абсолютным
APY. Стейкинг-жетон растёт независимо от протокола, и обещать конкретный
процент означало бы врать: senior видит «−2% к базовой», junior — «остаток».

Водопад потерь рисуется **в реальных пропорциях капитала**. Если junior тонкий,
это должно быть видно, потому что тогда защита senior слабее.
